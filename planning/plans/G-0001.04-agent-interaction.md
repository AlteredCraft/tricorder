## Proposal

### Hypothesis

A Python service running on the user's Mac over the local Wi-Fi network and an initially WebSocket-based protocol can guide a capture/compare interaction with bounded local response time, correct evidence references, prompt cancellation and safe recovery from stale messages or disconnection.

### Refuted if

A network/model wait blocks local instruments, responses refer to missing or wrong captures, stale commands act after cancellation/reconnection, queues grow during outages, or repeatable latency makes the proposed interaction unusable.

### Build

1. Implement bounded request/response messages with boot/session/request/capture IDs, deadlines and acknowledgements. Use device-side command validation and idempotency where retries could duplicate effects. The Tab5 initiates the connection to a configurable service address; keep the protocol independent of the Mac and model provider.
2. Use a scripted mock agent first. Request a photo, an audio capture and an A/B comparison, then return evidence-linked prompts. Inject delays, duplicates, reordered application responses, disconnections and stale responses.
3. Add a live provider adapter to the Mac service and timestamp the user turn, transfer, inference, first response, playback and cancel stages. Keep provider credentials on the service. Record service location and provider/model configuration; local service execution does not imply local inference. Begin with explicit turn-taking; include talk-over/interrupt trials before claiming continuous speech.
4. Run a handheld fan/sound investigation with camera context, steadiness guidance and spoken prompts. Compare WebRTC only if measurements identify a media/transport limitation; hold provider, codec, workload and network conditions constant where possible.

### Out of scope

This tests a bounded investigation protocol on the local network, not unrestricted remote execution or general scientific correctness. Hosted deployment, internet traversal, device authentication/provisioning for hosting, production encrypted transport and multiple users require later work. Bluetooth/Thread/Zigbee are deferred. A WebRTC comparison is not built unless triggered; local model inference has a separate future spike. A configurable endpoint establishes a deployment seam, not proof of hosted operation.

### How we know

Use the [shared evidence contract](G-0001.01-hardware-baseline.md#shared-run-evidence). Numeric limits are proposed acceptance targets, not verified performance.

1. Protocol: a transcript join on capture_id resolves every claim-bearing response to stored evidence/settings. Unknown IDs and expired/session-mismatched commands are rejected and logged; duplicates do not create duplicate captures.
   Deployment configuration: connect the same firmware build to two configured LAN service endpoints without source changes; record the endpoint and protocol version in each run. Verify that model calls and provider credentials remain service-side using the build configuration and sanitized request logs. Use an isolated development LAN for this experiment; do not expose the prototype as a public service.
2. Mock LAN: over at least 30 turns, proposed p95 command round-trip excluding capture/inference is ≤200 ms; local touch-to-submit stays ≤100 ms under .02's definition. Inject 5-second service delays and 30-second outages without blocking acquisition.
3. Cancellation/recovery: across 20 trials, local cancel-to-playback-stop p95 ≤150 ms, no old-session actions execute, and a restored transport establishes a fresh usable session within 5 seconds on the controlled LAN. Show delayed/offline state through logged transitions; do not rely on a screenshot as evidence.
4. Live agent: over at least 30 turns, report p50/p95/max time from device-detected end-of-turn to first audible response, with a proposed p95 target ≤2.5 seconds. Record endpoint-detection delay separately where measured. Failures are attributed to stages instead of assuming WebRTC fixes model latency.
5. Usefulness: operator completes three guided A/B sessions without keyboard intervention. Store scripted expected capture references, transcript audit and dated 1–5 responsiveness/usefulness ratings; target ≥4 in each session. This is a small formative assessment, not a general user-study claim.

Cross-run comparison: join summaries by spec revision and workload, retain all runs including failures, and compare at least three repetitions before claiming stable behavior. Differences in hardware, gain, clock, driver, model, codec or workload remain explicit.

### Candidate service architecture

Research and alternatives migrated from the former ADR-0002 on 2026-09-20. The Mac-first service is the agreed direction for experiments; the architecture has not yet been established by experiment evidence.

#### Context

A handheld investigation needs immediate feedback even when an agent is slow or disconnected. The agent must reference actual captures, and speech enhancement must not remove the signal under investigation.

#### Alternatives considered

1. **Local instruments with a Python service over WebSockets.** Simple, inspectable control and evidence protocol; application code owns media buffering and interruption.
2. **Local instruments with WebRTC media.** A candidate for continuous, interruptible conversation; adds signaling, codecs and media-session integration.
3. **Direct device-to-model integration.** Fewer service hops; more provider-specific session logic and credential lifecycle on the device.
4. **Entirely local reasoning.** Useful for bounded detection and commands; a general multimodal conversational agent on this hardware has not been established.

[FastAPI documents WebSockets](https://fastapi.tiangolo.com/advanced/websockets/). [Espressif's WebRTC solution](https://github.com/espressif/esp-webrtc-solution) provides capture, rendering and two-way-media examples. Their existence does not prove an unchanged Tab5 port or our latency targets. [ESP-SR](https://github.com/espressif/esp-sr) documents P4 speech-processing support.

#### Starting experiment direction

**Propose** local acquisition, measurement DSP, UI and immediate feedback, plus an asynchronous Python agent service, with FastAPI as an initial candidate. Evaluate WebSockets first. Keep model adapters replaceable; choose speech/model providers separately.

Start the service on the user's Mac, reached by the Tab5 over the local Wi-Fi network. Use a scripted mock agent first, then a live provider adapter. The service manages conversation context, assembles selected evidence for model requests, checks evidence references and coordinates model/speech services. Python is chosen for integration and experimentation; the service need not perform model inference itself.

Preserve a path to hosting this service later: use a configurable service address and a device-initiated connection, and keep the application protocol independent of the Mac and the model provider. Provider credentials stay on the service. A hosted deployment would remove the Mac dependency for conversation, while local instruments remain independent of service availability. Hosted deployment and its device authentication, encrypted transport, credential provisioning and capture-retention policy require a later spec; they are not part of the initial LAN experiment.

Use bounded commands such as request_capture, set_instrument_mode and cancel, with request IDs, deadlines, acknowledgements and device-side validation. A response references immutable capture IDs and their settings. Late responses from an earlier boot/session cannot change the active session. Acquisition never waits for an LLM response.

Propose separate audio paths:

- Measurement: retain pre-enhancement PCM and record physical channel mapping, sample rate, fixed gain, clipping and overruns.
- Conversation: derive a separate stream for resampling, VAD, AEC and noise suppression as needed.
- Alignment: retain sample counters and device timestamps; derive speech-processing delay from records.
- Playback: record speaker intervals. Keeping raw samples prevents software contamination but does not eliminate acoustic contamination from the device's own speaker.

Use a mocked agent before a live model to distinguish transport/device latency from inference latency. Consider WebRTC if measured continuous speech, interruption or media behavior warrants its complexity.

#### Costs and unresolved questions

The Python side remains easy to inspect and evolve. The device can operate its instruments offline. We must design flow control, reconnect/cancel semantics, evidence identity and clock alignment. During local R&D, conversation depends on the Mac service being available, plus provider connectivity when using a remote model. Hosting adds operational work and internet variability; local measurements do not establish hosted latency or reliability.

No full-duplex or agent-latency claim is accepted yet. [G-0001.03](G-0001.03-audio-integrity.md) tests audio separation; [G-0001.04](G-0001.04-agent-interaction.md) tests interaction and recovery. Revise this proposal if WebSockets cannot meet the workload's timing/buffering needs, and record a controlled WebRTC comparison before switching.

Privacy-sensitive captures and provider keys remain outside the public repository. This is a data-handling requirement for the experiment artifacts, not a new approval step.


#### Architecture follow-up

After .03 audio-separation results and each .04 mock/live-agent result, assess the architectural implications. Record decisions about the device/service boundary, evidence protocol or transport as soon as supporting evidence leads to an actual choice. A failed transport experiment stays recorded here with the next controlled comparison. Hosted deployment, local inference and full-duplex speech remain later work; they need not delay a bounded decision about the local deployment.
