# G-0001.04. Guide an investigation without blocking local instruments

Status: Not built
Goal: G-0001 — a trustworthy live investigation
Date: 2026-09-20
Revision: Initial proposal; no hardware results.

## Proposal

### Hypothesis

A Python service and initially WebSocket-based protocol can guide a capture/compare interaction with bounded local response time, correct evidence references, prompt cancellation and safe recovery from stale messages or disconnection.

### Refuted if

A network/model wait blocks local instruments, responses refer to missing or wrong captures, stale commands act after cancellation/reconnection, queues grow during outages, or repeatable latency makes the proposed interaction unusable.

### Build

1. Implement bounded request/response messages with boot/session/request/capture IDs, deadlines and acknowledgements. Use device-side command validation and idempotency where retries could duplicate effects.
2. Use a scripted mock agent first. Request a photo, an audio capture and an A/B comparison, then return evidence-linked prompts. Inject delays, duplicates, reordered application responses, disconnections and stale responses.
3. Add a live provider adapter and timestamp the user turn, transfer, inference, first response, playback and cancel stages. Begin with explicit turn-taking; include talk-over/interrupt trials before claiming continuous speech.
4. Run a handheld fan/sound investigation with camera context, steadiness guidance and spoken prompts. Compare WebRTC only if measurements identify a media/transport limitation; hold provider, codec, workload and network conditions constant where possible.

### Out of scope

This tests a bounded investigation protocol, not unrestricted remote execution or general scientific correctness. Bluetooth/Thread/Zigbee, internet traversal and multiple users are deferred. A WebRTC comparison is not built unless triggered; local model inference has a separate future spike.

### How we know

Use the [shared evidence contract](../stack-validation.md#evidence-contract-for-the-experiments). Numeric limits are proposed acceptance targets, not verified performance.

1. Protocol: a transcript join on capture_id resolves every claim-bearing response to stored evidence/settings. Unknown IDs and expired/session-mismatched commands are rejected and logged; duplicates do not create duplicate captures.
2. Mock LAN: over at least 30 turns, proposed p95 command round-trip excluding capture/inference is ≤200 ms; local touch-to-submit stays ≤100 ms under .02's definition. Inject 5-second service delays and 30-second outages without blocking acquisition.
3. Cancellation/recovery: across 20 trials, local cancel-to-playback-stop p95 ≤150 ms, no old-session actions execute, and a restored transport establishes a fresh usable session within 5 seconds on the controlled LAN. Show delayed/offline state through logged transitions; do not rely on a screenshot as evidence.
4. Live agent: over at least 30 turns, report p50/p95/max time from device-detected end-of-turn to first audible response, with a proposed p95 target ≤2.5 seconds. Record endpoint-detection delay separately where measured. Failures are attributed to stages instead of assuming WebRTC fixes model latency.
5. Usefulness: operator completes three guided A/B sessions without keyboard intervention. Store scripted expected capture references, transcript audit and dated 1–5 responsiveness/usefulness ratings; target ≥4 in each session. This is a small formative assessment, not a general user-study claim.

Cross-run comparison: join summaries by spec revision and workload, retain all runs including failures, and compare at least three repetitions before claiming stable behavior. Differences in hardware, gain, clock, driver, model, codec or workload remain explicit.
