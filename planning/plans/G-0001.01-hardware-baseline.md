## Proposal

### Hypothesis

A pinned native toolchain and explicit peripheral ownership can repeatedly initialize this Tab5's built-in capabilities, with observed inputs and outputs attributable to the configured hardware.

### Refuted if

Any required peripheral fails repeatably, two libraries compete for a shared resource, documented identity does not match detected hardware without a supported driver, or a clean rebuild cannot reproduce initialization. An unexplained blank display or absent sensor is a failure to investigate, not a reason to silently remove that capability.

### Build

1. Inventory board/display labels, P4 silicon revision, camera identity, flash/PSRAM and C6 firmware. Treat the supplied ST7121 screen label as a clue until confirmed.
2. Reproduce the factory demo using its documented toolchain and capture resolved component revisions. Keep a known recovery image and its flashing instructions.
3. Build a small native diagnostic with one owner for each I²C/I²S/display/camera resource. Exercise touch, camera, microphones, speaker/headphones, BMI270, RTC, INA226, SD and Wi-Fi individually.
4. Compare the official BSP with M5Unified/factory drivers for unsupported functions. Record which source supplies each capability, including IO-expander-controlled power and reset behavior.

### Out of scope

This baseline tests the individual built-in functions. It does not establish concurrent performance (.02), quantitative microphone calibration (.03), agent usefulness (.04), or battery life/wake reliability (.05). USB host/device and RS-485 functionality need suitable peripherals/fixtures and remain deferred if unavailable; do not equate enumeration of a controller with a working application.

### How we know

Use the [shared evidence contract](#shared-run-evidence). Numeric limits are proposed acceptance targets, not verified performance.

1. Inventory: manifest.json contains actual identities, detection method and driver source. The capability matrix records verified / failed / not tested with evidence paths. Investigate the camera-name discrepancy in the BSP documentation against an ID read where supported.
2. Reproduction: archive build/flash/boot logs from two clean builds using the same pinned inputs. Explain any nondeterministic binary differences. Complete 10 cold starts and 10 software resets with zero initialization failures for the selected core capabilities.
3. Diagnostics: retain camera frames; verify captured test sound and playback via recorded observation; touch events cover corners/center; IMU logs respond to known orientations; RTC timestamps advance; SD test-file checksum matches after readback; Wi-Fi completes a logged round trip. Record audio physical-channel mapping rather than assuming stereo.
4. Driver selection: capability records identify resource owners and missing coverage. No unexplained duplicate initialization. Every built-in sensing path is tested or explicitly unresolved; core camera/audio/motion/touch/storage/network failures block .02.

Cross-run comparison: join summaries by spec revision and workload, retain all runs including failures, and compare at least three repetitions before claiming stable behavior. Differences in hardware, gain, clock, driver, model, codec or workload remain explicit.

### Shared run evidence

Each experiment should produce a private/local run folder, not committed personal captures:

- `manifest.json`: run/spec ID; UTC date and monotonic clock definition; board, silicon, display, camera and C6 firmware identity; firmware commit; toolchain/component versions and lock hashes; configuration; fixture/setup; expected workload; calibration status.
- `events.jsonl`: run/session/boot IDs, event name, device monotonic timestamp, host receipt timestamp when applicable, sequence number, capture ID and relevant fields.
- `metrics.csv`: timestamped workload, frame/capture counts, rates, latency, queue depth, overruns, allocation failures, free internal RAM/PSRAM, largest free blocks, task stack high-water marks, reset reason and power readings.
- `captures/`: test PCM/WAV, images and checksums with rate, gain, format, channels, processing flags, and sample/frame counters.
- `summary.json`: each acceptance check, sample count, p50/p95/max where appropriate, missing-data count, pass/fail/inconclusive, and paths to source records.
- `operator-notes.md`: dated observations, fixture movements and usability ratings, explicitly distinguished from instrument measurements.

These are proposed record formats to implement in the spikes. They do not yet exist. Every build step gets its check before implementation; append results under that spec's Observed section. Missing evidence is inconclusive, not a pass.

Use device monotonic time for local durations; never subtract unsynchronized host and device timestamps. Record boot boundaries. Use round-trip timing or a measured clock-offset estimate for cross-device analysis, including uncertainty. A display flush callback measures software completion, not necessarily photon-visible response.

Keep sampling and calibration settings comparable for A/B runs. Change one independent variable at a time before combining loads. Retain at least three repeated runs for a claimed performance result. Do not use appearance of the UI as proof of correctness; record physical observations and timing in run artifacts.
